FeedBites 顧客帳本 設計規格

2026-09-13｜文件整理：JASON｜狀態：Jason 已核可設計方向（LINE Login、首張餐券），待審閱本文｜對客品牌名：常來點 EatAgain（2026-09-13 定案）

一、定義與目標

定義。FeedBites 是餐廳的顧客帳本。每一位客人從掃第一次 QR 開始，在這家店做的每件事都記在帳本上並換成點數：填問卷、補資料、許願、線上訂餐、到智取櫃自助取餐。點數換餐券，餐券把人帶回店裡，回店再產生新資料。菜單照片是這本帳的素材庫，未來所有行銷內容都從它長出來。問卷是帳本的第一頁，不是產品本身。

商業前提（Jason 2026-09-13 定）。每家店每月 NT$100，價格低到不必決策就能開。價值在跨店的客人網路：客人一個帳號走遍所有用這套系統的餐廳。因此對客人的品牌名要中文、好記、每家店桌上都看得到；FeedBites 作為店長後台名稱保留。核心軟體我們自己做；店家要人到場拍照、上傳菜單、整理素材等，另收服務費，外包給周邊團隊執行。

連鎖集團是主要通路。東方美早餐店先試用，之後推到弘爺漢堡等連鎖。要同時對總部有好處（看得到所有分店的客群、時段、許願與口碑，統一素材庫）、對分店有好處（自己的客人、自己的餐券、自己的許願牆，總部看得到但動不了）。因此資料模型從第一天就有「集團 → 分店」兩層。

第一個場域。欣殿萬飲（高雄駁二，東方美集團投資，殿長阿水）。已有 KIOSK、GraBox、KDS 等設備層，本期只做軟體層。第二個場域是東方美早餐店，走同一套。

第一期目標（本 spec 範圍）

明確不做（第二、三期）

  • 線上訂餐（第二期）。本期只在事件表預留 order_completed 事件型別，不做任何訂餐 UI 或 API。
  • 智取櫃取餐事件（第三期）。預留 locker_pickup 事件型別；接法沿用麥味登 GraBox 的 ebus 事件。
  • 跨店點數互通。本期身分跨店（一個 LINE 帳號），點數餘額以店為單位。原因：餐券由各店買單，A 店賺的點在 B 店用等於 A 店替 B 店付錢，規則要另議。
  • 原生 App。全部走手機瀏覽器與 LINE 內建瀏覽器。
  • 問卷題型與遊戲化前端重做。現有 12 種題型與 XP 動畫保留，只把 XP 從「動畫」變成「落地的點數」。

四、點數規則（預設值，店長可改）

事件預設點數防刷
survey_completed50同一 customer 同一店同一日只給一次；匿名填答不給，登入回填時才給
profile_field_added每欄 20（生日、居住區、來店頻率、性別、年齡層）customers.profile_awarded 記錄，每欄一生一次
wish_created10每 customer 每店每日最多 3 則；少於 4 個字不給
wish_adopted200店長後台手動標記，每則願望一次
voucher_exchanged−(cost_points)餘額不足拒絕；另有 voucher_issued（0 點）記錄見面禮券發放
expired−剩餘每日 cron 掃 expires_at < now() 的賺點行，扣未用餘額

到期。賺點行 12 個月到期。到期前 7 天，由平台 LINE 官方帳號推播提醒（見 §六）。麥當勞被罵最兇的就是點數默默過期，這條不可省。

首張餐券。customer 在某店第一筆 survey_completed 寫入時，自動發一張 cost_points = 0 的券。預設：NT$30 折抵券，30 天有效，單筆消費滿 NT$150 可用。面額由阿水依毛利調整，後台可改；此預設值只是讓系統能跑，不是定案。

兌換目錄。店長在 /dashboard/vouchers 設定「幾點換什麼」，預設兩檔：300 點換 NT$50 折抵、600 點換指定小點一份。原則是第一次消費就換得到東西，門檻不得高於一般客人兩次來店能累積的點數。

五、身分與登入

  • 匿名先填。掃 QR 進 /s/[surveyId] 不要求登入，沿用現有 device_key。
  • 完成頁領點。完成頁出現「用 LINE 登入，領取 50 點與一張餐券」。登入成功後：把本次 response 的 customer_id 回填、寫 ledger、發首張券。只回填本次這一筆，不回溯同 device_key 的歷史匿名回答，避免把別人的手機填答歸到自己帳上。
  • LINE Login 實作。手寫 LINE Login v2.1 OAuth（start／callback 兩支路由），scope profile openid。不用 NextAuth 第二實例，因為會和店長端共用 AUTH_URL、basePath 與 authjs.* cookie。顧客 session 是 HMAC 簽章的獨立 cookie fb_customer；src/lib/auth-allowlist.ts 的 email 白名單只管店長端，顧客端不套。
  • LINE 內建瀏覽器。LINE Login 在 LINE 內開最順，這是選 LINE 而非 Google 的原因之一。既有的 webview-detect 提示只保留給店長端 Google 登入頁。
  • 我的帳本頁 /w/[storeId]：餘額、最近 10 筆進出、我的餐券（含 QR／代碼給店員看）、許願入口、補資料入口（每補一欄即時顯示加點）。

六、推播

本期用一個平台級 LINE 官方帳號（品牌：常來點 EatAgain），不是每店一個。理由：跨店身分本來就在平台層，一個 OA 就能對所有客人推播；各店自有 OA 的串接留到第二期。LINE Login 時帶 bot_prompt=aggressive 邀客人加好友，沒加的人收不到推播，但帳本功能不受影響。

推播只有三種，全部走既有 src/lib/line/push.ts 擴充：願望被採納、點數 7 天內到期、餐券 7 天內到期。免費額度每月 200 則（見專案記憶），超過就先停「到期提醒」保留「願望採納」，不升級方案。

七、菜單素材庫

  • /api/ai/parse-menu 改為：先把原圖存進 menu_assets(kind=original)，再送 Gemini 辨識。原圖不再只留在瀏覽器。
  • 前端裁切後上傳的單品圖存為 kind=crop，parent_id 指回原圖，dish_id 掛菜品。
  • /dashboard/assets：依日期列出原圖，點開看該圖切出的菜品；可把整批原圖標成「舊菜單」（is_current=false），不刪。
  • 儲存沿用 src/lib/local-upload.ts（EC2 本機 + nginx）。kind=generated 保留給未來 AI 生成素材，本期不產。

八、分析：時段 × 菜品 × 客群

/dashboard/analytics 一頁，三個維度任選一或二個交叉，第三個當篩選。

維度來源分桶
時段responses.hour_of_day早 06–10、午 11–14、下午 15–17、晚 18–21、深夜 22–02（對應欣殿萬飲日簡餐、夜餐酒兩模式）
菜品answers 內 dish-group 的 dishId，舊資料以 dishName 比對單品、分類
客群customers 的 gender / age_band / visit_freq / home_area；匿名者歸「未知」依欄位

指標：填答數、平均評分、被點名喜歡次數、許願次數。匿名填答只有時段與菜品兩維，客群為未知，不丟棄。

總部視角

/hq/[brandId]：brand_members 才可進。同一個 cube 多一個「分店」維度，可看旗下所有店的時段、菜品、客群、許願匯總與各店餐券發放／核銷率；唯讀，不能改任何分店的問卷、餐券或許願狀態。素材庫同理，總部可瀏覽與下載旗下各店原圖，不可刪。這一頁是東方美總部試用時的主要賣點，第一期就做，但只做讀。

九、核銷與錯誤處理

  • POST /api/vouchers/[code]/redeem：店員（store_members）登入才可呼叫。以 UPDATE ... WHERE status='active' AND expires_at > now() 的影響列數判斷，0 列回 409（已用或過期），不做先查再改。
  • 點數不足換券回 402，訊息寫還差幾點。
  • ledger 寫入用 unique 約束擋重複，衝突視為已給過，回 200 不報錯。
  • LINE Login 失敗（取消、逾時）回到完成頁，本次 response 仍保留為匿名，點數不給，畫面說明「下次登入可再領」。
  • parse-menu 的原圖落地失敗時整個請求失敗，不進行辨識，避免出現「有菜品沒原圖」。

十、安全與個資

  • 顧客資料表只存 LINE sub、顯示名、頭像網址與客人自填欄位，不存 access token。
  • 店長端 API 一律以 store_id 過濾（沿用現有多店隔離模式）；顧客端 API 一律以 session 的 customer_id 過濾，不接受 query 帶 customer_id。
  • 隱私頁 /privacy 補一段：LINE 登入取得的資料、用途、刪除方式。
  • 涉及 auth 與 schema migration，完成後依全域規範派 fresh-context 審查，並送 Codex 三輪稽核。

十一、測試

  • 單元：points-engine 每種事件的給點與防刷；到期扣點；首張券只發一次。
  • 整合：匿名填答 → LINE 回呼（mock）→ response 回填 → ledger 兩行（問卷 50、首張券 0）→ 帳本頁顯示。
  • 並發：同一 code 兩個請求同時核銷，只有一個 200。
  • 遷移：既有 dish-group 問卷回填 dishId 後，舊 answers 與新 answers 在 cube 內數字一致。
  • 部署後三端截圖（桌面、iPhone、Android）依 DEPLOY_VERIFICATION.md。

十二、Skill 預查紀錄（治理原則二）

skill_preflight.py "問卷 點數 會員 loyalty 許願 訂餐 取餐 智取櫃 行銷" 命中 3 個：survey（即本專案，L1 只取知識）、market-competitors、market-seo（皆與本設計無關，L0 不採用）。點數帳、會員、許願、餐券、素材庫無現成模組，全部自建。相關既有知識：ai-advisor 的記憶模式不套用於顧客端（本期不做顧客 AI 對話）。
