FeedBites P0 啟用前置修復 — 設計規格

日期 2026-08-11　·　撰寫 AI CPO　·　階段 P0（欣殿萬飲正式啟用前）
依據 Claude + Codex 雙模型對抗稽核（2026-08-10），所有引用行號已由 Claude 逐一開檔核實

一、背景與決策脈絡

FeedBites 準備正式啟用給第一家真實餐廳客戶「欣殿萬飲」（高雄駁二）。老闆確認的目標優先序為 A. 店長每天真的會打開看、B. 收到夠多真實回饋以產出第一份 AI 分析、D. 跑通流程挖出系統問題； 明確排除 C（招商展示包裝）。

雙模型稽核找出四項嚴重問題。老闆隨後提供兩個現實前提，大幅改變風險計算：

前提一：目前只有一間店。→ 跨租戶資料外洩的實際風險趨近於零（沒有第二家店的資料可被跨）。

前提二：優惠碼被複製不擔心，視為行銷。→ 讓客人有佔便宜心態、主動宣傳來店，是刻意的商業策略。

這兩個前提沒有涵蓋的部分（本規格的核心理由）：

後台存放的是欣殿萬飲客人的姓名、電話、email。那是店家客人的個資，不是我們的資料 —— 外洩時受害的是店家，責任會回到系統提供方。「只有一間店」與「優惠碼當行銷」都不豁免個資風險。 因此本階段只保留與個資保護、資料完整性、可觀測性相關的修復，其餘全部移除。

明確不做

  • 嚴格優惠券核銷 API（原子性 claim、防重複使用、防偽造）—— 老闆決定當作行銷成本

  • xp_earned 伺服器端驗證（客人可自選獎勵等級）—— 同上
  • 成員角色權限分級（owner / manager / staff）—— 只有一間店，延後
  • RLS 與 Drizzle/NextAuth 架構重構 —— 延後，改以應用層授權為單一防線
  • 擋掉重複填寫 —— 刻意不擋，重複填寫是行銷策略的一部分

三、工作項細節

1. 登入改為 Google OAuth + email 白名單 必做

問題證據　src/auth.ts:16-31　authorize() 僅檢查字串是否含 @， 隨即 upsert 使用者並發出 session。無密碼、無驗證碼、無 OAuth。 src/app/api/auth/register/route.ts:27 有儲存密碼 hash，但登入流程完全不檢查。
實際後果　知道店長 email 的人即可登入後台，讀取全部客人聯絡資料、匯出 CSV、 或呼叫 /api/stores/[storeId]/reset 清空資料。

方案

  • 在 src/auth.config.ts 的 providers 加入 NextAuth Google provider（Edge 相容，可放在此檔）。
  • 新增 signIn callback：比對登入 email 是否在白名單內，不在則拒絕登入。
  • 白名單以環境變數 ALLOWED_LOGIN_EMAILS 提供，逗號分隔，比對前一律轉小寫並去除空白。
  • 移除 src/auth.ts 中的 Credentials provider 與 src/app/api/auth/login/route.ts 的無驗證登入路徑。
  • 保留既有 users 表的 upsert 行為（首次 Google 登入時建立使用者），但僅在通過白名單後執行。

環境變數（新增，值存入 ~/.credentials/global.env，本檔與程式碼不得出現明文）

AUTH_GOOGLE_ID=...
AUTH_GOOGLE_SECRET=...
ALLOWED_LOGIN_EMAILS=leechishen@gmail.com,<店長 Gmail>
驗收條件
  1. 白名單內的 Google 帳號可成功登入並進入 /feedbites/dashboard。
  2. 白名單外的 Google 帳號登入後被拒絕，導回登入頁並顯示明確訊息（非 500）。
  3. 舊的 email-only 登入路徑已不存在：直接 POST /api/auth/login 回傳 404 或 405。
  4. 未登入時存取 /dashboard 仍為 307 導向 /login。

2. 公開 PATCH 加約束 必做

問題證據　src/app/api/surveys/[id]/responses/route.ts:174-199 公開 PATCH 僅需 response_id 即可更新 phone / email， where 條件未綁定網址上的 survey id，亦無擁有權憑證。
同檔 :202-209　一旦帶入 email，系統會查出該筆 response 對應的優惠碼並寄出， 形成「將他人優惠碼寄至攻擊者信箱」的路徑，同時消耗共用的 Resend 額度（可被當作寄信跳板， Resend 帳號一旦被封鎖將影響所有專案）。

方案（不實作完整 claim token，取最小成本的兩道約束）

  • 綁定 survey：where 條件改為同時比對 responses.id = response_id 與 responses.survey_id = id（id 取自 URL params）。
  • 時間窗：僅允許 submitted_at 在 30 分鐘 內的 response 被修改；逾時回傳 403。 理由：此 API 的正當用途是「客人填完後補留電話 / email」，該行為必定發生在填答後短時間內。
  • 更新結果為 0 筆時回傳 404，不得靜默成功。
驗收條件
  1. 用 A 問卷的 response_id 對 B 問卷的 PATCH 端點發送請求 → 404，且資料未被修改。
  2. 對 30 分鐘前建立的 response 發送 PATCH → 403，且不觸發任何寄信。
  3. 正常流程（填完問卷後立即補填手機）仍可成功。

3. 錯誤日誌與 request ID 必做

問題證據　responses/route.ts:169 的 catch 區塊完全不記錄例外，僅回傳「伺服器錯誤」； 同檔 :46 GET 亦吞錯；:113 LINE 推播為 catch {} 全靜默。 package.json 無任何錯誤追蹤依賴，亦無測試 script。
實際後果　目標 D（挖出系統問題）在沒有日誌的前提下無法達成；店長回報「怪怪的」時無從查起。

方案（P0 只做最小可用，不引入 Sentry 等外部服務）

  • 新增 src/lib/logger.ts：輸出單行 JSON 至 stdout（EC2 由 Docker/journald 收集即可）。 欄位固定為 ts、level、event、request_id、 store_id、survey_id、response_id、msg。
  • 每個 API request 產生一組 request_id（crypto.randomUUID()）， 錯誤回應的 JSON 一併回傳該 id，讓店長截圖即可對應日誌。
  • 把所有空的 catch {} 與吞錯的 catch 補上 logger.error。
  • 禁止記錄完整電話、email、問卷答案內容。電話與 email 僅記錄遮罩後的形式 （例：09**-***-123、a***@gmail.com）。
驗收條件
  1. 刻意讓提交失敗，容器日誌中可查到含 request_id 與 survey_id 的錯誤行。
  2. 錯誤回應的 JSON 內含同一組 request_id。
  3. 用真實電話與 email 填答一次，日誌中不得出現完整號碼或完整信箱。

4. getSelectedStore 補 user_id 條件 順手修

問題證據　src/lib/store-context.ts:36-40 查詢 membership 時僅比對 store_members.store_id = storeId，未比對 user_id。 只要該店存在任一成員即判定通過；而決定看哪家店的 feedbites_store_id 是使用者可自行修改的 cookie。
現況風險　因目前只有一間店，實際可利用性趨近於零。修復成本為單一 where 條件， 低於記錄技術債的成本，故納入本階段。

方案：where 改為 and(eq(store_members.store_id, storeId), eq(store_members.user_id, userId))。

驗收條件　使用者 A 手動把 cookie feedbites_store_id 改成非其擁有／非其成員的 store id， 重新整理後不得看到該店資料，應退回自己的第一間店或空狀態。

5. 優惠券店員手動標記已使用 設計調整

問題證據　discount_codes 具備 is_used、used_at 欄位 （schema.ts:96-97），src/lib/discount.ts:21-23 甚至定義了 already_used 狀態，但全專案沒有任何一行將 is_used 設為 true —— 僅在建立時寫入 false（responses/route.ts:144）。 儀表板 dashboard/surveys/[id]/page.tsx:78 統計 usedCodes， 因此該數字永遠顯示 0。
為何要處理　老闆已決定不做嚴格核銷，但儀表板持續顯示明顯錯誤的「已使用 0 張」會讓店長判定 系統不可信，直接損害目標 A（店長每天願意打開）。

方案（純記帳工具，不防重複、不防偽造，符合「優惠碼當行銷」的決定）

  • 店長後台的優惠券清單，每筆加一個「標記已使用 / 取消標記」切換按鈕。
  • 新增 PATCH /api/discounts/[code]/mark，需登入且該 code 屬於目前選定的 store。
  • 寫入 is_used 與 used_at；允許取消（改回 false 並清空 used_at）。
  • 儀表板文案由「已使用」改為「已核銷（店長標記）」，明確表達這是人工記錄而非系統驗證。
驗收條件
  1. 店長點擊標記後，重新整理仍為已標記狀態，used_at 有值。
  2. 儀表板「已核銷」數字隨標記即時反映，不再恆為 0。
  3. 未登入呼叫該 API → 401；用他店的 code → 404。

6. 裝置識別碼與 AI 分析去重 設計調整

問題證據　src/app/s/[surveyId]/SurveyClient.tsx:18-21 防重複提交函式被停用並永遠回傳 false，程式碼註解為 Disabled: allow unlimited submissions for testing。
決策　老闆決定不擋重複填寫（佔便宜心態有助宣傳），但目標 B 要求 AI 分析可信。 若同一人填十次被算成十個人，第一份 AI 報告會建立在被放大的單一意見上， 導致依錯誤結論調整菜單 —— 比沒有報告更糟。因此改為照常發券、但標記來源。

方案

  • 新增 migration 020_response_device_key.sql： ALTER TABLE responses ADD COLUMN IF NOT EXISTS device_key TEXT;， 並建立索引 idx_responses_device_key。同步更新 src/lib/db/schema.ts。
  • 前端在 localStorage 保存一組隨機 UUID 作為 device_key（不存在則產生）， 提交時一併送出。此值不含任何個人資訊。
  • 後端原樣寫入，不做任何阻擋，發券行為完全不變。
  • AI 分析與統計端（/api/ai/feedback-*、洞察頁）以 device_key 分組： 同一 device_key 的多筆回應在意見分析時只取 submitted_at 最新的一筆 （不做合併，避免同一人前後矛盾的答案被拼成不存在的意見）， 在發券張數統計時仍分別計算。device_key 為 NULL 的舊資料一律各自視為獨立填答。
  • 儀表板同時呈現「總填答數」與「不重複裝置數」兩個數字，讓店長看得出行銷聲量與真實客數的差別。
驗收條件
  1. 同一瀏覽器連續填 3 次 → 拿到 3 張券（行為不變），儀表板顯示「總填答 3 / 不重複裝置 1」。
  2. AI 分析輸入的資料集中，該裝置僅出現一次。
  3. 清除 localStorage 後再填 → 視為新裝置（已知限制，接受）。

7. 確認並處置 Vercel／EC2 雙部署 順手修

問題證據　專案同時存在 Vercel 綁定（.vercel/project.json， project prj_kTepX6…gAPC）與 EC2 部署（Dockerfile、scripts/deploy-ec2.sh、 scripts/nginx-feedbites.conf）。vercel.json 設有 cron /api/cron/knowledge-refresh（每週一 18:00），該路徑未含 /feedbites 前綴， 與 next.config.ts:5 的 basePath 不一致。 專案 CLAUDE.md 仍記載「推上 GitHub 後 Vercel 自動部署」，與實際跑在 EC2 的現況不符。
未能確認　Vercel 專案是否仍在部署、cron 是否啟用、兩邊是否共用同一 DATABASE_URL。 此為靜態稽核無法判定的部分，須實際查證。

方案

  • 查 Vercel 專案的最新部署狀態與 cron 執行紀錄。
  • 若仍在運作：確認其 DATABASE_URL 是否指向同一資料庫。是則立即停用該部署 （移除 production domain 或暫停專案），避免雙寫。
  • 確定 knowledge-refresh 這支 cron 的唯一執行者（EC2 system cron 或 Vercel 擇一）， 並修正路徑使其與 basePath 一致。
  • 更新專案 CLAUDE.md 的部署段落，改為 EC2 實況。
驗收條件
  1. 能明確回答「正式站是哪一套、cron 由誰跑」，並寫入專案 CLAUDE.md。
  2. 不存在第二套連向同一資料庫的運行中部署。
  3. knowledge-refresh 有一次可驗證的成功執行紀錄。

七、端到端驗收（P0 完成的定義）

以下流程須在真實手機上跑通，桌面 + iPhone + Android 三端截圖全過才算完成 （依全域規範 DEPLOY_VERIFICATION）：

  1. 店長用白名單內 Google 帳號登入後台，非白名單帳號被拒。
  2. 手機掃桌上 QR → 開啟問卷 → 填答 → 取得優惠碼。（Safari 與 Chrome 各測一次）
  3. 店長在後台看到該筆回饋，點「標記已核銷」，數字更新。
  4. 同一手機再填一次 → 仍可取得優惠碼，儀表板顯示總填答 2 / 不重複裝置 1。
  5. 刻意送出錯誤請求 → 回應含 request_id，日誌可查到對應行，且日誌內無完整電話／email。
  6. 確認正式站只有 EC2 一套在跑（Vercel 專案狀態需查明並處置）。

P0 期間的暫時管制：在工作項 1（登入驗證）完成部署前， 不對外發布任何 FeedBites 連結或 QR，包含測試用途。
